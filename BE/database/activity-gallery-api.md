# Activity gallery

`POST /api/v1/admin/activities` accepts multipart form data:

| Part | Content | Required |
| --- | --- | --- |
| `request` | Activity information JSON, without `imageUrls` | Yes |
| `image` | Thumbnail file | No |
| `images` | Gallery files; repeat this part for each file | No |

The backend uploads `image` and `images` using the existing Cloudinary service.
Gallery URLs are generated by Cloudinary and stored in file order; clients upload files rather than submitting URLs.
Thumbnail is separate from the gallery. Missing gallery files result in an empty gallery.

```javascript
const form = new FormData();
form.append('request', new Blob([JSON.stringify(activityRequest)], {
  type: 'application/json'
}));
if (thumbnail) form.append('image', thumbnail);
for (const file of galleryFiles) form.append('images', file);
await fetch('/api/v1/admin/activities', {
  method: 'POST',
  headers: { Authorization: `Bearer ${token}` },
  body: form
});
```

Let the browser set the multipart Content-Type boundary.

`GET /api/activity/{activityId}` returns `data.imageUrls` as an ordered JSON array,
alongside the existing `data.thumbnailUrl`. Activities without gallery images return `[]`.
The create response retains its existing shape; gallery URLs are available through detail.

Persistence uses `activity_images`. The current `ddl-auto: update` configuration creates
the table on startup. For deployments using managed schema changes, apply
`database/activity-images.sql` before deploying. No production database migration was run
as part of this code change.

Gallery upload uses the same Cloudinary configuration and folder as existing uploads.
Tests mock Cloudinary; they do not upload files to the live account. If an upload fails,
the activity is not saved. Files already uploaded before a later failure are not
automatically removed from Cloudinary, consistent with the existing upload service.
